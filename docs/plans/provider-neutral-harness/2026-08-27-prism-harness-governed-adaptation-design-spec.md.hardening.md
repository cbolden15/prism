# Hardening report — historical-worktree/docs/plans/provider-neutral-harness/2026-08-27-prism-harness-governed-adaptation-design-spec.md

**SINGLE-ENGINE REPORT — Codex did not contribute.** Codex CLI failed to start on two attempts ("Error: failed to initialize in-process app-server client: Operation not permitted (os error 1)", plus a PATH-alias creation warning with the same "Operation not permitted" error) — an environment/sandbox permission issue, not a review or content judgment, and no output was produced to extract findings from. Everything below comes from four independent Claude review lenses (SECURITY, FEASIBILITY, SCOPE, DESIGN) only; treat it as one engine's pass, not a two-engine reconciliation.

**Verdict:** the document has two design-level Critical gaps — an approval flow that binds a human sign-off to an unreadable digest, and a quarantine rule that appears to forbid the evaluation step the document itself requires — plus eight Important gaps spanning an unspecified emergency-rollback bypass (raised independently by two lenses), an invalid enforcement-kind value, a dead-end lifecycle state, two scope-creep items against a locked precedent, and two cross-section trust-boundary/invariant inconsistencies. All 11 input findings were evidence-checked before reaching this pass; one pair was merged as the same root cause seen from two lenses, leaving 10 distinct findings below.

## Critical

- [ ] Owner promotion approval binds only a digest, not readable content — Section 15 (lines 498-500) specifies the operator channel displays only `candidateId`/`contentDigest` and the base-version transition ("A renderer-supplied description is not approval input"), with Section 553's renderer summary explicitly disclaimed as non-authoritative for the approval decision. The sibling D8 spec's parallel human-approval gate (`2026-08-26-prism-harness-goal-execution-design-spec.md` section 12.2, lines 477-484) requires the operator channel to "echo the exact reservation content being approved," a materially stronger bar. An attacker who gets malicious candidate bytes through capture, quarantine, deterministic scanning, and evaluation, and manipulates the LLM-based independent reviewer into a `promote` recommendation, faces an owner who can only see a 64-character hex digest — not the content — before their one-time approval binds those exact bytes into a durable `memory`/`prompt-addendum` destination. (claude:SECURITY) — fix: require the operator channel to echo a safe, non-executable rendering of the actual candidate content — not just its digest — as a mandatory approval precondition, mirroring D8 section 12.2, and specify how that rendering is produced without itself becoming an injection/spoofing surface (e.g., deterministic plain-text extraction with no markup interpretation, produced by a component distinct from the untrusted reviewer).

- [ ] Quarantine's absolute "no loader into prompts" rule blocks the design's own evaluation step — Section 7 (line 181) and Section 12 (lines 355-357) state quarantine "has no loader path into prompts, skills, tools, task registries, or executable code" in unqualified terms, while Section 13.2 step 3 requires running "the immutable evaluator" against candidate bytes and Section 22 starts the whole D9 rollout with `memory` and `prompt-addendum` candidates (lines 698-699). Measuring whether a candidate prompt addendum improves behavior against the charter's objective requires composing it into a bounded test prompt — exactly the "loader path into prompts" the document forbids in absolute terms, making the D9-INV-01/02 invariants that cite this rule ambiguous about whether isolated evaluator composition is a violation. (claude:DESIGN) — fix: split the quarantine rule into two explicit clauses — (1) quarantine content may be composed into an isolated, budget-bounded, non-canonical evaluation or review prompt under the evaluator's/reviewer's own admitted identity, with no persistence or promotion effect, and (2) it can never be composed into an active/canonical/production prompt, tool, registry, or executable path — and update Section 7, Section 12, and D9-INV-01/02 to reflect the distinction.

## Important

- [ ] Emergency rollback fast path has no stated scope for what it may bypass — raised independently by two lenses on the same two sentences (Section 15, lines 511-514): "Rollback selects a previous immutable version through the same resolver, approval, expected-base, and receipt path. Emergency rollback may use an owner-authenticated fast path, but it still records the exact transition and cannot erase the faulty version or its evidence." The first sentence commits rollback to the full four-gate path; the second carves out an unqualified emergency exception with no statement of which gate(s) it relaxes. D9-INV-08 (line 634, "expected-base conditional, idempotent by operation ID, reconcilable after lost acknowledgement") and Section 18's failure-fallback table (lines 573-574, "No failure falls back to direct writes, latest-version resolution, ... or unbounded retry") neither bind nor exempt this path. During a live incident, an operator or a compromised owner-authenticated channel could invoke the fast path in a way that skips expected-base CAS, one-time operation IDs, or the resolver's precondition checks (candidate state, evidence digests, destination class) — the text's phrasing (an alternative to "the same resolver ... path") invites exactly that reading. This is independently corroborated: SECURITY framed it as an undefined resolver bypass risk under a compromised-credential scenario, DESIGN framed it as a contract ambiguity that two implementations of Plan L could resolve two different ways under incident pressure; both anchor on the identical two sentences and neither found any other mention of "fast path" anywhere in the document or the wider corpus. (claude:SECURITY, claude:DESIGN — independently corroborated) — fix: enumerate exactly which resolver preconditions (candidate state, evidence digests, expected base version, idempotent operation ID) the emergency path may never skip, name the owner-authentication step that substitutes for whichever normal approval-channel step it does skip, and state this next to Section 18's failure/recovery table rather than as a parenthetical in Section 15. If the fast path is meant to be a genuine bypass for incident response, define its reduced precondition set explicitly and add a dedicated invariant and risk-table row for it.

- [ ] Secret leakage into a promoted candidate has no compensating control, unlike other risk classes — Section 12 lists secrets/credentials/tokens as a deterministic-scanner check, but the Section 23 risk table gives prompt injection four layered controls ("Quarantine, instruction scanning, independent review, exact owner approval") while secret leakage has no risk-table row or fallback control at all. Section 17 only promises secrets "never enter renderer summaries or model review prompts" (display-time filtering, not a purge of stored quarantine bytes), and Section 12's dedup requirement mandates retaining rejected candidates — including any rejected for containing secrets — for future comparison. If the deterministic scanner has a false negative on an unusual token format, nothing downstream re-checks: the evaluator and reviewer aren't described as re-scanning, and Section 15's digest-only approval (see the first Critical finding above) means the owner can't visually catch a leaked credential either — it promotes into a durable destination with no second gate. (claude:SECURITY) — fix: add secret leakage to the Section 23 risk table with an explicit defense-in-depth control — a second, independently-maintained secret-scanning pass at promotion time distinct from the quarantine scanner, plus a mandatory redaction/purge requirement for any quarantine bytes a scanner flags as containing credentials.

- [ ] D9-INV-08 uses an enforcement kind (`fault-injection`) not in the closed vocabulary — line 634 assigns D9-INV-08 the enforcement kind `fault-injection`, but the ratified architecture spec's closed set (`2026-08-26-prism-harness-architecture-design-spec.md:1043-1049`, D6 Section 18.1) is exactly `runtime-adversarial`, `static-structure`, `generated-document-consistency`, `controlled-performance-qualification`, `release-or-architecture-gate` — `fault-injection` is not a member, and Plan A's `EnforcementKind` TS union matches the same closed set. Both source documents sit above D9 in its own precedence list (lines 56-60). The sibling D8 spec correctly labels its analogous destination/idempotency invariants (`PNH-INV-48/49/52`) `runtime-adversarial`, and the D8 hardening review already flagged this exact defect class (Important 7, `COHERENCE-7`) for a different pair of invariants. Plan L1's own exit gate (Section 21) requires registering D9-INV-08 in the Plan A registry; because `fault-injection` isn't in the closed union, the registry parser rejects the entry at registration time, and D9 has no authority under its own precedence rules to add a new enforcement kind unilaterally. (claude:FEASIBILITY) — fix: change D9-INV-08's enforcement kind from `fault-injection` to `runtime-adversarial` (matching the D8 precedent for destination/idempotency invariants tested via fault-injection kill points), or explicitly split the row so any non-runtime-testable component gets a valid closed-set kind.

- [ ] Candidate lifecycle has no transition out of `ambiguous`, contradicting the reconciliation requirement — Section 10's closed state table (lines 305-315) lists only `promoting -> promoted | ambiguous` with no further row starting from `ambiguous`, and line 317 states "No transition moves backward" with no carve-out — the section explicitly calls this a closed lifecycle. But Section 15 (lines 507-509) requires that after a lost acknowledgement "the candidate becomes `ambiguous`. The writer reconciles by operation ID and exact destination digest," and Section 19's `DestinationWriter.reconcile` (line 608) is typed `DestinationReceipt | AmbiguousReceipt` — the same successful-write receipt type `apply()` uses — implying reconciliation can conclusively confirm a committed write. When a promotion write actually succeeded but the acknowledgement was lost, `reconcile()` confirms the commit via operation ID and digest, but the candidate's own state field has no legal move to `promoted` under the literal Section 10 table, so an implementer following the state machine exactly cannot mark the candidate resolved — violating the document's own verification criterion 3 ("closed, immutable, idempotent, and explicit about ambiguity"). (claude:FEASIBILITY) — fix: add an explicit `ambiguous -> promoted | rejected` (or equivalent) transition to the Section 10 state table describing exactly what reconciliation is allowed to resolve to, so the lifecycle table and the `reconcile()` interface / Plan L1 exit gate agree.

- [ ] Autoresearch evaluator-optimizer subsystem is unrequested scope against the locked precedent — Section 13, Milestone L2 (experiment-charter schemas, isolated workspaces, mutation-envelope enforcement, hidden holdout support, finite stop rules, an autoresearch-style reference experiment), and D9-INV-06/07 build an entire bounded evaluator-optimizer/search subsystem. D9's own precedence chain (Section 2, item 3) names `2026-08-19-hermes-inspired-pnh-followup.md` as the locked durable-learning boundary, whose binding instruction (lines 231-239) requires any capability beyond the predecessor plan's Task 6 to get "its own plan," reusing Task 6 "verbatim" — and Task 6 (`2026-08-18-x1-hermes-inspired-dsh-followup.md`, lines 542-593) never mentions an evaluator-optimizer loop, experiment charters, holdout sets, or search-based candidate generation. Neither "verbatim" nor "Task 6" appears anywhere in the D9 document, so this deviation from the higher-precedence source is never surfaced or reconciled, despite Section 2's own rule that "where a higher source conflicts with D9, the higher source wins." If ratified as written, engineers build a materially larger optimization-loop architecture than the locked "terminal-event-only generation + quarantine + scan + review + one-time approval" design ever authorized, justified only by one sentence in Section 1. (claude:SCOPE) — fix: either strip Section 13, Milestone L2, D9-INV-06, and D9-INV-07 and defer the evaluator-optimizer capability to a separately proposed and ratified follow-up plan, or add an explicit paragraph in D9 naming the conflict with the locked "reuse Task 6 verbatim" instruction and recording the owner's decision to supersede it.

- [ ] Promotion writer grants direct destination-write authority that Task 6 explicitly excluded — Section 7 defines the "Promotion writer" as a component that itself "applies an authorized transition and records the destination receipt," and Sections 15/19 give it CAS-conditional, idempotent, versioned, rollback-capable direct writes to Brain or `agent-config`. The locked Task 6 design D9's precedence chain requires reusing verbatim (`2026-08-18-x1-hermes-inspired-dsh-followup.md`, lines 574-579) instead limits the mechanism to exporting "a sanitized capture stanza for the existing Brain capture pipeline, a patch proposal for a later `agent-config` workflow, or a runtime evidence/backlog item" and states plainly "This X1 plan performs none of those destination writes itself." D9 also expands the candidate-kind taxonomy from Task 6's 3 target classes to 5 (`CandidateKind`, Section 7/10), adding `task-template` and `executable-extension` with no basis in the locked design. If Plan L1 is implemented as written, engineers build a second, parallel promotion mechanism (idempotency, CAS, rollback, ambiguity reconciliation) directly into the same canonical store the existing capture/curation pipeline already curates, rather than emitting an artifact for that pipeline to consume through its existing review path. Section 22's language about integrating "through supported consumer-side write paths rather than create a second canonical store" is the closest thing to a rebuttal but doesn't clearly establish that `DestinationWriter` merely triggers the existing pipeline rather than mechanically applying the write itself. (claude:SCOPE) — fix: either narrow D9's promotion mechanism back to "export an approved artifact for the existing capture pipeline to consume" (dropping the writer's own write/rollback/reconciliation authority and the two candidate kinds with no basis in Task 6), or add an explicit, named amendment paragraph acknowledging and superseding the locked Task 6 constraint with the owner's sign-off.

- [ ] "Candidate generator" is placed on opposite sides of the public/consumer trust boundary in two sections — Section 9's topology diagram (lines 236-263) draws "candidate generator" as a box under the consumer adaptation plane, downstream of "evidence reader (read-only)." Section 7's vocabulary (line 183) and Section 11 (line 343) instead define it as "A D8 run that proposes candidate bytes... artifact-only authority" — matching D8's own vocabulary, where "artifact-only" denotes an admitted, kernel-side run with no outward-effect grants, and D8's boundary section (lines 436-437) frames generation as happening inside D8, with only the resulting artifact exported outward. An implementer following Section 9 alone would build "candidate generator" as a new consumer-side service that independently produces `AdaptationCandidate` bytes outside `pnh/`; an implementer following Section 7/11 and D8's own model would instead admit a D8 prompt-role run whose settled artifact already conforms to D9's schema — meaning `pnh/` itself would gain some knowledge of D9's candidate schema. These are materially different systems with opposite consequences for Decision #2 ("public kernel exports only generic evidence... no `learning`/`memory`/`research` plugin kind in public `pnh/`," Section 6) and for D9-INV-09, and the document gives no signal for which reading is authoritative. (claude:DESIGN) — fix: redraw Section 9 so "candidate generation" is shown as an ordinary D8-admitted artifact-only run inside the kernel column, and rename the first consumer-side box to something like "candidate ingest/packaging" that only translates already-generic D8 evidence into the typed envelope; align the Section 7 vocabulary entry and Section 11 prose to the same model.

- [ ] D9-INV-04's "active runs retain their version" guarantee doesn't cover the destinations D9 actually names — D9-INV-04 (line 630) states "Promotion affects only future runs; active runs retain every admitted prompt, context, task, tool, route, budget, and proof version," and Section 7/22 name "Brain or `agent-config`" as the worked-example destinations, with existing Brain and `agent-config` capture pipelines said to "remain canonical." This session's own CLAUDE.md loads `historical-agent-config/fragments/core/*.md` via plain `@include` at parse time with ordinary unversioned git commits and no content-digest pin, admission step, or version-selection API at the read side (verified against the actual agent-config repo's git log). If D9 promotes a new fragment version mid-day, a background subagent spawned hours after its parent session started, or a fresh nested session opened as part of the same in-flight work, would pick up the newly promoted bytes immediately — there is no described admission/pinning mechanism for consumer-side prompt-fragment reads, only for D1-D8 kernel run admission. D9-INV-04's plain-language claim can't be verified or enforced for the exact destination class the document uses as its own example. (claude:DESIGN) — fix: either narrow D9-INV-04's statement explicitly to D1/D8-admitted runs and add a separate, clearly-non-invariant note that external destination adapters are individually responsible for (and may not provide) read-side version pinning, or require every eligible destination class to expose a version-pinning read API as a Milestone L1 entry condition before D9 may write to it.
