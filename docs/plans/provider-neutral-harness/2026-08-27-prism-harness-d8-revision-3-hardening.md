## Critical

- [ ] Destination-policy checks validate a declared target, not the actual write footprint of an operation (codex) — goal-execution-design-spec.md:447-501 defines a single canonical-reservation-target check against policy, and :786-790 treats that as the complete protected-destination control; nothing requires an operation to declare every resulting write path or execute through a non-escaping filesystem capability. A tar with a `../../Library/Application Support/prism/prompts/role.md` entry granted under an artifact-output policy rooted elsewhere writes the protected path with no second reservation or canonical-target check — fix: require a complete effect-footprint contract (every final write target independently declared and checked), mandate containment-preserving primitives (dirfd/openat-style no-follow traversal), reject archive/shell/recursive operations that can't enumerate and confine their writes, and add traversal/rename/symlink/multi-file fixtures to Plan I.

## Important

- [ ] Write-target check is checked-then-used, not atomically bound to the actual write (TOCTOU) (claude:SECURITY) — :495-501 scopes D4's canonical/symlink-resolved re-check to "reservation and permit time inside the settlement transaction"; :594 confirms writes go through that same reservation/permit/receipt path; D8-INV-10 (:976) is worded only in terms of permit issuance, never the moment of the write syscall, and no fd/inode capture, O_NOFOLLOW, or immediate pre-syscall re-check exists anywhere in the document. Swapping the reserved target's symlink between permit issuance and tool dispatch — plausible given the doc's own acknowledgment of concurrent in-flight reservations within a run (:970) — redirects a permitted write into a D9-protected destination — fix: bind the resolved canonical target atomically to the write (captured fd/inode, O_NOFOLLOW, or a re-check with no scheduling gap before the syscall) and add a Plan J exit-gate test that swaps the target mid-flight. Adjacent to the Critical finding above (both are destination-policy-lags-the-write gaps) but a distinct defect: this one is a timing race on a target that *was* correctly checked, not a missing check on additional write paths — kept separate rather than merged.

- [ ] No read-side equivalent to DestinationPolicy — granted read tools have no path confinement (claude:SECURITY) — `destinationPolicies` (:424-452, :482-501) and D8-INV-10 (:976) are write-only; the example manifest (:328) grants a generic `fs-read` tool with no allowed-root list; run evidence is exportable to D9 as a candidate artifact (:771-777) and surfaced in the decision-queue renderer (:824-830); a full-document grep for any read-side analogue returns nothing, and the same taxonomy is absent from the ratified D1-D7 spec. An untrusted model-proposed action can point `fs-read` at `~/.dev-secrets.env`, `~/.ssh/id_rsa`, or a D9-protected instruction store, and the content flows into evidence with no rejection — fix: add a read-side `readablePolicies`/`ReadPolicy` mirroring DestinationPolicy, require D1 to reject grants lacking allowed source roots, require D4 to re-check canonical/symlink-resolved read targets, and add a sibling invariant plus Plan I/J fixtures for read-target rejection.
