D8 revision 2 and its D8-D9 boundary amendment declare a hard ban on D8 ever writing to a D9 protected destination class, but neither document contains a mechanism that checks a grant against that list at admission or a write's target against it at permit time — the ban is prose, not enforcement. Five further Important-severity gaps remain in prompt-composition binding, digest determinism, budget-comparison semantics, active-time enforcement, and a sandbox-property citation that names a control the parent spec never actually grants.

Engines: Claude (lenses SECURITY, FEASIBILITY, SCOPE reported; **DESIGN failed to complete and contributed no findings** — treat architecture/design-quality coverage for this revision as incomplete pending a re-run) and Codex, both run independently against the same two review targets (D8 goal-execution spec rev 2, D8-D9 boundary amendment). 3 raw findings were killed during audit before reaching this reconciliation; the 7 below all survived independent evidence and failure-scenario verification.

## Critical

- [ ] **The D9 protected-destination ban is declarative prose — no structural check exists at admission or at permit issuance, independently found by both engines** — Both the D8 spec (Section 11.5, lines 693-700) and the boundary amendment (Section 3.2, lines 59-72) assert that D8 "cannot write or authorize writes to" five protected classes (including the admitted task/plugin/tool/grant/route/budget/evaluator registries themselves), but this is stated as a declarative absence, not an enforced rule — unlike every other D8 boundary (the requestedBindings-subset rule at lines 435-437 and the encapsulated-outward-effect restriction at lines 449-451), which are phrased and fixture-tested as active admission checks. Two independent gaps compound this: (1) admission-time — TaskDefinition's `grantedBindings.tools` (lines 408-420) are plain string plugin IDs with no effect-class/destination taxonomy anywhere in the corpus (grep for "effect class taxonomy", "EffectClass", "effect family" returns nothing), so nothing at admission checks whether a granted tool's effect family intersects a protected class; (2) permit-time — `SelectionState.requireSelection` (lines 827-831) validates only selection identity, ratification, owner-domain, round, and artifact digest, never a write's actual target/destination, so D4 has nothing to check a granted `fs-write`-style effect's target path against before issuing a permit. Plan I's rejection-fixture list (line 905: "entrypoint on prompt, grant exceeding request, outward grant without verification, interleaved placement") has no fixture class for either gap. — fix: Add a closed effect-class/destination-capability taxonomy that a tool grant's registered effect family is checked against at admission (rejecting any grant whose effect family intersects the five D9 protected classes), **and** bind every writable effect to an exact destination/target policy that D4 re-checks and rejects at reservation and permit issuance regardless of what selection or approval already passed. Add a corresponding Plan I/J rejection-fixture class ("grant targeting a protected destination class") covering absolute paths, traversal, symlinks, and destination aliases, and cite the specific D1/D2 mechanism that performs each check.

## Important

- [ ] **Encapsulated-profile trust model cites a Section 16.3 network-restriction property that section does not grant** — D8 Section 9.1 (lines 452-455) requires "recorded production proof" that the Codex adapter's artifact-only profile is "read-only sandbox, network-restricted, isolated working directory, per parent Section 16.3," but the ratified architecture spec's actual Section 16.3 (lines 972-991) grants only "an isolated temporary working directory and the narrowest supported Codex sandbox" — no sentence there, or anywhere else in either document (confirmed by full-document grep for "network"), establishes read-only or network-restricted behavior for the adapter. Section 10.6's entire justification for treating encapsulated interior tool calls as invisible to D4 settlement rests on this property existing. — fix: Correct the D8 Section 9.1 citation to stop attributing a property to Section 16.3 that it doesn't grant. Require the Plan I/J "recorded production proof" obligation to independently build and adversarially verify actual sandbox-level network/filesystem restriction (e.g., a test that attempts and fails an egress connection from inside the sandbox) rather than allowing it to be satisfied by citing parent text that doesn't say this.

- [ ] **No comparison semantics defined for numeric budget fields in the "grant must be a subset of request" admission rule** — The admission rule at lines 435-437 ("grantedBindings must be a subset of the prompt plugin's requestedBindings") is worked out for list-valued (`tools`) and equality (`routeClass`) fields, but never states a comparison rule for the numeric budget fields (`maxTurns`, `maxEffects`, `maxActiveSeconds`) carried in the Section 13.1 admitted-run snapshot — despite line 905 explicitly naming "grant exceeding request" as a required Plan I rejection-fixture class. A full-document grep finds no numeric-subset definition anywhere. — fix: Extend the subset rule to state explicitly that admission rejects any task definition where `grantedBindings.budgets.<field>` exceeds `requestedBindings.budgets.<field>`, for each of `maxTurns`, `maxEffects`, and `maxActiveSeconds`. Add a fixture under "grant exceeding request" that specifically exercises the numeric budget fields, not only tools/routeClass.

- [ ] **TaskDefinition does not bind the complete set of prompt fragments composed into it, so an added fragment changes behavior without changing the digest** — D8 (lines 342-344) allows request-free prompt fragments to compose into an agent role, and (lines 371-384) digests every contributing admitted fragment, but `TaskDefinition` (lines 408-420) records only a single `promptPluginId` — no fragment-identity list or exact-version set — and `taskDigest`'s claimed coverage (lines 458-461) does not name this composition set either. — fix: Add an ordered, exact-version prompt-set binding (or a single composition-set digest) to `TaskDefinition`, fold it into `taskDigest`, and require admission and the PromptComposer to reject any run whose actual composed fragments are missing, extra, or version-drifted relative to that binding.

- [ ] **`pnh-compose-v1`'s "canonical serialization" for the composed-prompt digest has no defined byte encoding** — D8 (lines 354-359) claims an exact byte grammar and reproducible digest, but the digest definition itself (lines 381-384, SHA-256 over a "canonical serialization") never specifies field order, UTF-8/escaping rules, integer encoding, or length framing — and the parent architecture spec, which D8 cites for `taskDigest`, never operationalizes "canonical serialization" either. — fix: Specify a normative byte encoding for the digest preimage (field order, UTF-8 rules, integer encoding, length delimiters, null handling, domain-separation prefix) and publish test vectors including delimiter-sensitive identifiers and Unicode, so two conforming implementations cannot diverge.

- [ ] **`maxActiveSeconds` can be exceeded by an in-flight dispatch before any check observes it** — D8 (lines 582-589) persists elapsed active time only at effect transitions and a registry-bounded interval, with no requirement that this interval fit inside every admitted budget, and no permit deadline bound to remaining active-time budget; the turn protocol (lines 507-524) allows dispatch immediately once reservation succeeds. A task admitted with `maxActiveSeconds: 1` and a provider call that runs 30 seconds against a 60-second accounting interval reserves while the accumulator reads zero and runs well past its budget before any update or receipt can observe the overrun — directly contradicting D8-INV-04's claim (Section 14.2) that "D4 refuses reservations beyond the admitted... active-time budgets" and that concurrent reservations "can never jointly exceed a budget." — fix: Require every dispatch permit to carry a monotonic deadline no later than remaining active budget, require broker cancellation/timeout at that deadline, constrain the accounting interval relative to the minimum supported budget, and define the terminal outcome for a timeout that occurs after permit consumption.
