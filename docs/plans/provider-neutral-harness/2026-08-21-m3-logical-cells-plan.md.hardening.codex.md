# Codex hardening findings — 2026-08-21-m3-logical-cells-plan.md

Two critical, five important, and one minor finding survived evidence re-check. The direct M3 suite can go green while the production command channel still blocks across allocations; the plan also misses an existing process-wide counter, leaves cell and shutdown custody underspecified, cannot execute its protocol amendment as written, overclaims conformance, and does not actually keep the constitution gate out of the sandbox.

## Critical

- [ ] Production command dispatch remains one global fault cell — Task 1 reroutes the supervisor methods listed at `docs/plans/provider-neutral-harness/2026-08-21-m3-logical-cells-plan.md:170-176`, while the M3 suite calls those methods directly at `pnh/tests/m3-plugin-fault-isolation.test.ts:270-277`; the production loop still awaits each dispatch and result write before parsing the next buffered command at `pnh/harness/plugin-container-supervisor.mjs:778-820`. Failure: plugin A blocks in `docker.remove()`, and plugin B's already-buffered `status` or `write` command is never dispatched into B's cell until A releases, even though all ten direct-method tests can pass. — fix: include `runSupervisorCommandLoop` in Task 1, track concurrent validated command tasks, serialize only frame writes, await outstanding tasks on loop termination, and add a command-loop-level blocked-A/progress-B test. [codex]

- [ ] The plan's “no cross-plugin aggregate counters” stop condition is already tripped — the plan asserts no such counter exists at `docs/plans/provider-neutral-harness/2026-08-21-m3-logical-cells-plan.md:95-99`, but the shared command loop owns one lifetime-wide `cumulativeBytes` counter and throws when all allocations together cross 8 MB at `pnh/harness/plugin-container-supervisor.mjs:775-781`; that throw reaches the process-wide shutdown path at `pnh/harness/plugin-container-supervisor.mjs:852-860`. Failure: valid attributed commands for allocation A consume the shared command-byte budget, then B's next command crosses the limit, tears down the command loop, and causes every allocation, including B, to be cleaned up. — fix: stop at the plan's checkpoint and obtain an owner decision: either classify this as an accepted shared-channel failure and leave PNH-INV-01/-22 proposed, or authorize per-allocation metering plus a narrow bounded aggregate arbiter/reset policy before activation. [codex]

## Important

- [ ] Cell creation and disposal have no lifecycle that preserves both bounded memory and retained receipts — the plan creates a persistent cell before allocation state exists and disposes it only when an allocation is removed at `docs/plans/provider-neutral-harness/2026-08-21-m3-logical-cells-plan.md:88-93`, but launch can return an acknowledged tombstone or throw on an unadmitted launch before `allocations.set` at `pnh/harness/plugin-container-supervisor.mjs:294-325`; terminal settlement itself retains the allocation at `pnh/harness/plugin-container-supervisor.mjs:248-266`, and only acknowledgement removes it at `pnh/harness/plugin-container-supervisor.mjs:446-457`, as required by `pnh/tests/plugin-container-supervisor.test.ts:233-249`. Failure: distinct rejected launches leave cells with no allocation-removal path; deleting state at terminal cleanup to satisfy Task 1's reclamation wording instead breaks terminal `status`, `acknowledge`, and replay behavior. — fix: specify an explicit open/terminal/acknowledged/disposed cell state machine, dispose pre-allocation failures in `finally`, retain or separately tombstone terminal receipts through acknowledgement, define late `onClose`/stream behavior, and verify exact-once disposal through an injected test factory rather than a production debug export. [codex]

- [ ] `Promise.allSettled` can turn lost cleanup custody into successful shutdown — the plan mandates shutdown fan-out with `allSettled` but does not require rejection inspection at `docs/plans/provider-neutral-harness/2026-08-21-m3-logical-cells-plan.md:81-86`; current shutdown propagates an unexpected cleanup rejection at `pnh/harness/plugin-container-supervisor.mjs:460-471`, while process exit trusts only the returned receipt list at `pnh/harness/plugin-container-supervisor.mjs:837-844`. Failure: one cell rejects during cleanup, an unchecked `allSettled` omits its receipt, the remaining receipts are all `confirmedAbsent`, and the supervisor exits successfully without evidence that the rejected cell's container is absent. — fix: require one settled result per snapshotted allocation, throw on every rejected or missing result after all cells have been attempted, and add a two-cell shutdown test where one cleanup rejects and shutdown must fail closed. [codex]

- [ ] Task 2 uses the schema hash where the locked binding hash is required and contradicts the protocol's version rule — the plan supplies `sha256:15a4...` as `from_hash` at `docs/plans/provider-neutral-harness/2026-08-21-m3-logical-cells-plan.md:203-208`, but protocol bindings hash `{version, schema_hash}` at `pnh/contracts/registry.ts:239-243` and amendments must match the lock at `pnh/contracts/registry.ts:283-301`; PNH-PROTO-02's locked hash is `sha256:6566f8e88df81546c63fa3f1e1e3b8b7cd4d5164a50f0d28fdce1e463f471c08` in `pnh/contracts/invariants.lock:1`. The plan also keeps version 1 at `docs/plans/provider-neutral-harness/2026-08-21-m3-logical-cells-plan.md:198-207`, while the spec says every schema-source change requires a version bump at `docs/plans/provider-neutral-harness/specs/supervisor-command-channel.md:7-11`. Failure: `--update-lock` refuses the stated amendment; substituting the correct hash while retaining version 1 violates the pinned spec. — fix: use the locked binding hash, replace the nonexistent PNH-INV-03 YAML amendment precedent with `pnh/tests/constitution-registry.test.ts:184-190`, and resolve the version-policy conflict before execution: preferably narrow the pin to a wire-only schema module, or explicitly amend the policy; under the current text, bumping to version 2 requires owner approval because it conflicts with the plan's no-wire-change scope. [codex]

- [ ] Task 3 activates broader invariants than its suite proves — PNH-INV-01 covers blocking, settlement, and contamination at `pnh/contracts/invariants.yaml:3-12`, and PNH-INV-22 covers queues, timers, byte limits, concurrency, cleanup, evidence, and unattributed sequencing at `pnh/contracts/invariants.yaml:280-288`; Task 3 activates both using only the M3 file at `docs/plans/provider-neutral-harness/2026-08-21-m3-logical-cells-plan.md:227-232`, whose “protocol failure” and “malformed output” cases are identical manual cleanup calls at `pnh/tests/m3-plugin-fault-isolation.test.ts:217-227` and whose assertions cover only direct-method status/write progress at `pnh/tests/m3-plugin-fault-isolation.test.ts:270-299`. Failure: the production command loop and shared byte counter above can still violate both invariants while the registered conformance file passes and the constitution reports them active. — fix: keep PNH-INV-01/-22 proposed until production-path tests cover their binding statements; at minimum add real malformed/identity/event-contamination cases and independent timer, input/output byte, cleanup, and evidence isolation cases before activation. [codex]

- [ ] Task 4 does not keep the constitution gate host-side — it limits changes to `package.json` and merely inserts the host command before the sandbox at `docs/plans/provider-neutral-harness/2026-08-21-m3-logical-cells-plan.md:240-250`, but `run-sandbox.mjs` passes no test selection by default at `pnh/harness/run-sandbox.mjs:76-78`, and the container then recursively discovers every `pnh/tests/*.test.ts` file at `pnh/harness/sandbox/container-entrypoint.mjs:106-108`. The discovered constitution gate spawns `repoRoot/node_modules/.bin/tsx` at `pnh/contracts/coverage.ts:11-23`, while the image installs dependencies under `/runner` at `pnh/harness/sandbox/Containerfile:5-10` and mounts only `pnh/` under `/sandbox` at `pnh/harness/run-sandbox.mjs:98-113`. Failure: the host gate passes, then the sandbox runs it again without `/sandbox/node_modules` or the repository's `/sandbox/docs`, so the required full regression remains red. — fix: extend Task 4 to define an explicit host-versus-sandbox test manifest or make the sandbox runner exclude host-only constitution suites while still auto-including the M3 suite; verify the selected sandbox file list in a non-Docker unit test. [codex]
