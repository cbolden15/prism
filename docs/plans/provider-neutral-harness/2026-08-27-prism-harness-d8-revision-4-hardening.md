## Critical

- [ ] Write-side destination policy omits the credential-store exclusion that the read-side policy has — Goal-execution spec lines 515-534 (write-side destination-capability enforcement) and D8-INV-10 (line 986) enumerate only five protected classes and never mention credential stores; the read-side rule at lines 556-564 and D8-INV-11 (line 987) explicitly add "or a credential store" as a sixth exclusion. A project-wide grep for "credential" across both review targets returns exactly two hits, both read-side, zero write-side. Failure scenario: a `DestinationPolicy.allowedTargetRoots` entry resolving to an API-token file or SSH-key directory matches none of the five enumerated write-side protected classes, so D1 admits it and D4's D8-INV-10 check authorizes the write — a task-payload-steered agent (task payload is untrusted per Section 8.3) can overwrite or plant credential material. claude:SECURITY, evidence-verified by independent audit (grep confirmed, no counter-text found). — fix: add "or a credential store" to the write-side enforcement paragraph (~531-534) and to D8-INV-10 (line 986), matching the read-side wording verbatim.
- [ ] Protected-destination taxonomy diverges between the D8 body and the higher-precedence boundary amendment — D8 body Sections 9.1 (line ~519) and 11.2 (line 798) enumerate "prompt, instruction, skill, task-template, and/or workflow-template stores" (no procedural-guidance category, template-qualified workflow stores only). The boundary amendment Section 3.2 (lines 72-73) — ranked above the D8 body in D8's own Section 2 precedence list (item 4 vs. item 5) — enumerates "prompt, instruction, procedural-guidance, skill, task-template, or workflow stores": an added category plus unqualified "workflow stores." Plan I structurally implements Section 9.1's narrower list per Section 15's deliverables. Failure scenario: a plugin registers an operation under effect family "procedural-guidance-store-write" or "workflow-instance-store-write" (a live, non-template workflow record); D1 admission checks against Section 9.1's narrower enumeration, finds no match, treats the family as ordinary and grantable, and admits a `DestinationPolicy` targeting that store — durably writable by an agent, exactly the class of write the amendment's Section 3.2 says no D8 artifact can authorize. claude:SECURITY, evidence-verified by independent audit (both enumerations confirmed verbatim, precedence order confirmed, no reconciling text found). — fix: reconcile the two enumerations to identical wording — add "procedural-guidance" to Sections 9.1 and 11.2 and widen "workflow-template stores" to "workflow stores" (or explicitly narrow the amendment to match, if templates-only is actually intended).

## Important

- [ ] `evidenceExpectations` field on `TaskDefinition` traces to no goal, plan, or admission rule — Line 465 (`evidenceExpectations: EvidenceExpectation[]`) and the line-237 vocabulary-table mention are the field's only two occurrences anywhere in the repo (repo-wide grep confirmed); the Section 9.2 goal-contract mapping table (lines 605-614) has no row deriving it from any owner input; the referenced `EvidenceExpectation` type is never defined; Plan I's exit-gate fixture enumeration (1009-1018) never mentions it. Failure scenario: an implementer building Plan I's admission validator has zero specified semantics, admission rule, or test fixture for a field that sits on the canonical admitted artifact — it is either silently dropped (falsifying the Section 6 vocabulary claim) or given invented, unspecified semantics, the exact unspecified-authority-widening pattern the rest of the document forecloses. claude:SCOPE, evidence-verified by independent audit (all citations confirmed, undefined type confirmed as compounding gap). — fix: remove the field and its vocabulary entry as speculative generality on the core admitted artifact, or defer it to whichever future decision area specifies its semantics, admission rule, and exit-gate fixture — consistent with how the work-program subsystem was already split out of this revision for the identical reason.
- [ ] Read-side D4 reservation check never re-verifies the actual descendant target against protected/credential classes — D8 Section 9.1 (lines 556-564) rejects a source root only when the root itself resolves into a protected class or credential store; D8-INV-11 (line 987) then re-checks a read reservation's source only for "outside the admitted roots," with no "or inside a protected destination class" clause at all — unlike D8-INV-10 (write, line 986), whose invariant text explicitly carries both disjuncts ("outside the admitted destination-policy roots OR inside a protected destination class"). Failure scenario: a task is admitted with `allowedSourceRoots=[".../pnh"]`; the model then proposes reading `.../pnh/contracts/invariants.lock` — the root is allowed and not itself protected, so D8-INV-11's root-only check passes even though the actual target is protected constitutional proof-status state. codex, evidence-verified by independent audit (both invariant texts confirmed verbatim; the asymmetry between D8-INV-10's two disjuncts and D8-INV-11's one is the auditor's own finding, not present in Codex's original framing). Related to, but a distinct defect from, the write-side credential-store omission above: that one is a missing taxonomy entry: this one is a missing check-type on the read path only. — fix: add the same "or inside a protected destination class" disjunct to D8-INV-11 and require D4's read-reservation check to re-verify the actual canonical target — not just the admitted root — against the full protected/credential taxonomy; add an ancestor-root/descendant-target adversarial fixture.
- [ ] Claimed complete write footprint excludes intermediate mutations — Lines 535-540 require only "every final write path an operation produces" to be declared and checked; confinement is required only "when the complete write set cannot be enumerated before execution" (541-548); D8-INV-10 and the reconciliation table (986, 1215) repeat the final-path framing. Failure scenario: a tool declares one final output path, but before producing it overwrites `.../pnh/contracts/invariants.lock`, copies derived data into the declared artifact, then restores the lock — the protected mutation is an intermediate write, not a final output, so nothing in the enumerable-footprint bucket requires it to be declared or checked, and confinement (which would catch it) applies only to the unenumerable-footprint bucket. codex, evidence-verified by independent audit (quotes confirmed verbatim; the TOCTOU-closing bullet was checked and found to only make the checked final write atomic, not to add coverage for undeclared intermediate writes). — fix: define the footprint as every filesystem mutation (temp files, parent creation, renames, deletes, metadata changes, hard links, final writes), require all to be predeclared or routed through a single descriptor-confined capability, and add a protected-intermediate-write test.
- [ ] Approval-wait active-time suspension has no durable state transition or restart rule — Lines 714-717 exclude approval-wait time from active accounting; lines 739-744 define the cross-epoch restart rule for the ACTIVE accumulator only. No persisted approval-wait state, atomic entry/exit condition, or rehydration rule is defined for a restart occurring while a run is suspended (Sections 10.5, 12.1-12.3 checked, none found). Plan J's exit gates (1046-1061) test restart during an active budget but not a pending approval across an epoch, while the reconciliation table (1178) nonetheless claims suspension is evidenced. Failure scenario: a run with `maxActiveSeconds=60` reserves an approval-gated outward effect after 10 seconds, then waits two hours across a daemon restart; the replacement daemon sees only parent active run/effect records, so it either charges the elapsed wait against the active budget (violating the stated suspension exclusion) or treats the run as suspended with no durable, reservation-bound condition, letting a suspended run outlive an approval denial or expiry. codex, evidence-verified by independent audit (all citations confirmed; no concrete rule closing the gap found anywhere in the reviewed sections). — fix: add a durable, reservation-bound approval-wait substate with transactional suspension-start/decision-or-expiry-end recording, an accumulator checkpoint, and an epoch-rehydration rule; test approval pending, denial, expiry, and daemon replacement at each boundary.
