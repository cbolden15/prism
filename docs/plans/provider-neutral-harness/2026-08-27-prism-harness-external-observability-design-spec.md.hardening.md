# Hardening report — /private/tmp/prism-d10-hardening-review-manifest.md

Five engines (claude:SECURITY, claude:FEASIBILITY, claude:SCOPE, claude:DESIGN, codex) reviewed the D10 external-observability design spec and the D9 boundary amendment; 13 findings survived independent evidence-checking and one pair merged on root cause, leaving 12 distinct findings (1 Critical, 10 Important, 1 Minor). The Critical finding blocks the D9→D10 external-evaluation loop outright (no governed way to get candidate content into Langfuse at all), and the Important cluster — alias-key governance, an undefined "exporter principal," and two independently-found gaps in collector-ingress authentication — should be closed before implementation starts.

## Critical
- [ ] No governed write path for candidate content into Langfuse; only manual, ungoverned egress exists — §6 bars any Prism execution principal from holding write-capable Langfuse access (MCP/CLI/API/agent); §13 restricts the collector's sole export credential to OTLP telemetry; §15 prohibits any component from storing backend API credentials; §17 only says Langfuse "may store and display" the dataset snapshot (no writer named); yet §21's M3 exit gate requires a real Langfuse experiment/dataset to exist for `ExternalEvidenceAdapter.fetchExact` to read back, and D9's `ExperimentCoordinator` interface (admit/record/stop) never references Langfuse or any submission call. The only remaining path is a human pasting candidate/dataset content directly into the Langfuse UI/API, entirely outside the projector allowlist (§12), collector redaction (§13), and local-only/secret classification (§12) that the rest of the document relies on for its "privacy is default-deny before data reaches the collector" claim (§3.4) — fix: either explicitly scope a governed, out-of-band human-curation upload procedure (with its own redaction/review gate) as part of D10's boundary and state no Prism execution principal performs it, or add a scoped, separately-credentialed "experiment submission" component outside §6's prohibited list and update §19's authority matrix and §6's non-goals accordingly. (claude:DESIGN)

## Important
- [ ] OTLP collector ingress has no authenticated per-owner-domain/per-principal binding, enabling spoofed or cross-tenant telemetry injection — independently corroborated by claude:SECURITY and codex from two angles on the same gap: §13 requires only "OTLP over an authenticated local channel or TLS" (line 427) for ingress, never stating that pipeline/backend-project routing derives from the authenticated transport identity of the sender (vs. self-declared OTLP resource attributes), nor requiring client-identity binding to one projector principal, owner-domain pipeline binding, or source rate limits. §9's cross-owner-channel claim and D10-INV-02/D10-INV-08 assume this is closed; §18's shared-homelab-NUC deployment discussion makes a shared-collector topology plausible. Two complementary failure paths follow: (claude:SECURITY) two owner domains sharing one collector — a compromised projector for domain A sends OTLP batches with resource attributes claiming to belong to domain B, and if the collector routes by self-declared attributes rather than authenticated channel identity, it injects fabricated telemetry into B's Langfuse project; (codex) any untrusted local process that reaches the TLS-only receiver (which authenticates the server, not the client) can submit spoofed OTLP spans using a copied owner alias and forged `terminal_status`, then flood max-size batches to evict legitimate ones — fix: require collector pipeline/backend-project selection to derive from authenticated transport identity (distinct mTLS client cert or Unix socket with restrictive ownership per owner/projector principal, not payload-declared attributes), add receiver-side owner-pipeline routing and per-principal rate/size limits, and either mandate one collector process per owner domain or specify the isolation control that makes a shared collector safe. (claude:SECURITY, codex — independently corroborated)
- [ ] No custody, storage, or access-control decision for the owner-domain HMAC alias key — §12 (lines 389-399) defines `alias = HMAC-SHA-256(key[telemetry-alias-key-version], canonical-value)` for every local-correlation identity and says only "the owner-domain-specific key and canonical value stay local"; the secret classification at lines 401-413 enumerates credentials/tokens/headers as always-secret but never the alias key itself, and it appears in neither the Authority Matrix (§19) nor any storage/rotation/access-control mechanism anywhere in the document — fix: classify the alias key with credential-equivalent custody rules (generation/storage location, which process may read it, rotation cadence/procedure) and add it as a governed artifact in the Authority Matrix. (claude:SECURITY)
- [ ] Exporter-compromise recovery procedure omits alias-key rotation — §14's failure table states the response to "Exporter compromise" is only "Backend credential revocation and cursor rebuild from committed evidence" (line 486); §12 confirms rotation is the supported remedy for a compromised key ("Rotation creates new aliases and does not silently join old and new identities," lines 398-399) but the exporter-compromise row never invokes it, so a leaked alias key remains valid for deterministic de-anonymization of all past/future exports even after "recovery" — fix: add alias-key rotation to the Exporter compromise row (and any row implying projector-process compromise), requiring new-key issuance and treating old aliases as compromised going forward. (claude:SECURITY)
- [ ] "Exporter principal" used as authority anchor but never defined — lines 279-280 ("Each reader instance is authenticated and bound to one owner domain and one exporter principal") and line 326 use the term to gate `EvidenceProjectionReader` authentication, but it appears nowhere in the Vocabulary table (§7), the Authority Matrix (§19), or the ratified D1-D7 architecture spec's principal taxonomy (grep confirmed zero matches against "Host custody service principal" / "Per-user provider broker principal" / "execution principal"). Note: this is the D4 read-side binding — distinct from the separate OTLP-collector-ingress gap above — fix: add "exporter principal" to the Vocabulary table with an explicit definition, and either map it onto the existing execution-principal/custody-service-principal taxonomy with a concrete authentication mechanism, or name it explicitly as a second additive D1-D7 seam in §9/§19. (claude:FEASIBILITY)
- [ ] D10 dataset-curation step introduces a "train" role with no goal grounding — §17 (line 601) requires curation to "assign train, evaluation, holdout, or adversarial role before candidate work," but D9's ratified non-goals explicitly exclude "model-weight training as a Prism kernel responsibility" (line 157), and neither D8 nor D9 uses "train"/"training" anywhere else; nothing in D9's evaluator-optimizer loop (baseline/generate/evaluate/recommend/stop) consumes a "train" split the way it does holdout/adversarial sets — fix: drop "train" from §17's role list (keep evaluation/holdout/adversarial, which are grounded in D9's existing controls), or if intentional for iterating on D9's non-model "durable learned state" artifacts, add one sentence tying it to that concept with an explicit cross-reference to D9's non-goal. (claude:SCOPE)
- [ ] Backend replay-safety assumed, not required as an ObservabilityBackend admission criterion — §13.5 and §14's failure table rely on replaying the same stable batch on ack loss, and §15 admits Langfuse only as an `ObservabilityBackend` implementation with §9/§22 naming a "future backend" as a first-class swap target, but neither §10's interfaces nor §19's authority matrix requires a backend to dedupe/upsert by stable trace/span ID before admission — fix: add an explicit backend-admission requirement (dedupe/upsert by stable trace and span ID) in §10 or §19, plus an exit-gate test verifying duplicate-batch replay produces no duplicate visible spans before a new backend is approved. (claude:DESIGN)
- [ ] D10-INV-02 mixes a static-structure fact with a runtime-only correlation guarantee under one enforcement kind — §20 tags D10-INV-02 ("no observability component reads or writes settlement storage directly or correlates owner domains") as a single `static-structure` invariant, but "no direct settlement-storage access" is a static import-graph fact while "does not correlate owner domains" depends on runtime behavior of the HMAC alias-key derivation (§12) — a static-structure check (e.g., an AST/module-graph lint) would never catch a runtime fallback to a shared key across owner domains, and the ratified architecture spec's closed enforcement-kind taxonomy assigns exactly one kind per invariant — fix: split D10-INV-02 into a static-structure invariant ("no direct settlement-storage access") and a runtime-adversarial invariant ("alias derivation never joins two owner domains under one key"), matching the one-kind-per-invariant precedent already established elsewhere in this program. (claude:DESIGN)
- [ ] Collector acknowledgement can permanently lose telemetry — §14 advances the exporter cursor on an unspecified "acked" result while §13 permits bounded in-memory batches/queues; no passage defines "acked" as durable collector acceptance or confirmed backend persistence. A batch can be placed only in RAM, acked (cursor advances past it), then lost if the collector crashes before forwarding it, with no defined reconciliation to detect the gap — fix: advance the D4-derived cursor only after a collector-owned durable queue receipt (batch digest + sequence range) or backend acknowledgement, and require startup reconciliation between D4 ranges, exporter receipts, and collector receipts. (codex)
- [ ] Collector redaction leaves OTLP envelope fields outside the closed policy — §13's two-layer redaction (projector allowlist, then a "second closed attribute allowlist in the collector") scopes both layers to attributes only; span names, status messages, event names/attributes, links, resource/scope fields, and tracestate are independent OTLP envelope fields never covered by either allowlist, so a projector regression that puts a secret into a span name or status message (e.g., `status.message="POST /Users/alice/private/repo"`) passes through unredacted — fix: specify a complete OTLP-envelope schema at collector ingress (fixed closed span/event names, no status descriptions, no links/tracestate, closed resource/scope fields, bounded lengths) that rejects rather than sanitizes unknown envelope fields, with prohibited-value fixtures per field location. (codex)
- [ ] The external-evidence reader has no pre-buffering resource limits — §16 requires the adapter to obtain canonical response bytes and perform two complete reads, with its only stated bound being a charter pagination limit; no response-byte, per-item, field-length, decompression, or timeout limit is specified before untrusted backend data reaches the reader, so one item with multi-GB compressed metadata can exhaust the adapter host's memory/disk and block all imports for that owner domain — fix: add charter-pinned hard limits (compressed/decompressed bytes, page/item count, field length, nesting, deadlines) enforced via streaming parsing before canonical-byte persistence, with a bounded fail-closed receipt on any limit breach. (codex)
