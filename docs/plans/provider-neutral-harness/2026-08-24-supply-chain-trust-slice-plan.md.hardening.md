# Hardening report — historical-worktree/docs/plans/provider-neutral-harness/2026-08-24-supply-chain-trust-slice-plan.md

Two Critical defects survive: the pre-spawn re-check can be pointed at a different tree than the frozen launch spec it is supposed to protect, and Task 2's mandated `invariants.yaml` edit makes `npm run test:constitution` fail as written, so the task cannot complete on its own instructions. Everything below traces to a finding raised by one of four engines — gpt:SECURITY, gpt:FEASIBILITY, gpt:SCOPE (three lenses run inside Codex on an OpenAI model) and claude:independent — and each survived an independent evidence audit before reaching this report.

Engines that ran: **gpt:SECURITY**, **gpt:FEASIBILITY**, **gpt:SCOPE**, **claude:independent**. Twelve findings arrived (one more was killed before reconciliation); two pairs merged into one finding each, leaving ten.

**Resolution (applied 2026-08-25).** All ten are addressed in the plan. Four of them — one Critical and three Importants — were resolved by removal rather than by patch: the owner read the concentration of defects in the snapshot machinery as evidence against the mechanism itself, dropped snapshots entirely, and moved the guarantee to launch-side re-derivation (D8, amended cycle 5). A fifth (the byte-budget half of the untrusted-read finding) survives that removal and is conceded in Risks with a Deferred fix. The owner also decided disclosure accepts any genuine `AdmissionTicket` and carries owner approval as an explicit provenance field (D4, amended cycle 5), which resolves the SCOPE Important. Each checkbox below records which of those applies. Nothing here has been re-verified by a confirming pass.

## Critical

- [x] **Mutable snapshot-root map lets the pre-spawn check verify a different tree than the frozen launch spec** *(gpt:SECURITY)* — `pluginSnapshotRoots` is a `ReadonlyMap` only in the type system (plan 2180-2184); the plan itself concedes at 2434-2449 that `Object.freeze` on a `Map` does not stop `set`/`delete`. `assertOwnerApprovedSnapshotUnchanged` re-reads the root from that map every call (2888-2896), while the spec froze `cwd`/`entrypointPath` at build time (`plugin-spawn-launch-spec.ts:319-328`) and the supervisor spawns from the frozen values (`plugin-spawn-supervisor.mjs:316-332`, `:464`). Failure: build a spec pointing at snapshot A, run `(ticket.pluginSnapshotRoots as Map).set("alpha", cleanCopyB)`, tamper A, call the pre-spawn assertion — it hashes B, passes, and the supervisor executes tampered A. This is the exact TOCTOU narrowing the cycle-4 amendment exists to provide, so it is defeated at its own gate. — fix: key the snapshot roots in a module-private `WeakMap` on the ticket instead of an exposed map, or have `assertOwnerApprovedSnapshotUnchanged` take the exact spec (or an opaque handle minted with it) and verify the path the spec actually froze; add a negative test that swaps the map entry between spec construction and the assertion and requires a throw. — **resolved by removal (cycle-5 pivot), plus the second half of the fix applied as written.** There is no map: `pluginSnapshotRoots` and the snapshot roots it indexed are gone with the snapshot mechanism (D8, amended cycle 5). The renamed `assertOwnerApprovedLaunchSpecUnchanged` takes the spec and re-derives against `spec.cwd` and nothing else — no lookup, no second parameter naming a directory — so the two sources of truth this finding exploited no longer both exist. Task 5's review gate (Step 2b, check 2) is written to fail if any future edit reintroduces the indirection, and Task 2b carries a tamper-after-spec-creation test that requires the throw.

Failure: append the line, run `npm run test:constitution`, check 5 fails on drift — Step 5's own expected outcome is unreachable. — fix: add `constitution.md` to Task 2's Files list and to the Task 5 / Verification diff allowlist (plan 3816-3821), and put `npx tsx pnh/scripts/generate-constitution.ts --write` into Step 5 before the suite run. The lock-neutrality reasoning is unaffected — `bindingHash` still covers `statement`/`bounds` only, so no amendment record is needed. — **applied as written, with one correction to the fix's own path.** Step 5 now runs `npx tsx pnh/scripts/generate-constitution.ts --write` before the suite run, the regenerated document is in Task 2's Files list, and it is in both Task 5 Step 2's outside-`pnh/` allowlist and Verification step 3's diff allowlist. ## Important

- [x] **The pinned launch path cannot run this repository's existing spawn plugin, which turns D8 into a plugin-packaging redesign** *(gpt:FEASIBILITY + gpt:SCOPE, raised independently under different titles and merged here)* — the snapshot contains `manifest.json` plus exactly the declared files at a new path (plan 2211-2250), while `pnh/host-tests/fixtures/spawn-plugins/pid-reporter/index.mjs:1` imports `../../../../kernel/plugin-runner/entrypoint.mjs` and its manifest declares only `index.mjs`. Failure: admit that fixture through the pinned path and launch it — the specifier resolves outside the snapshot and the child dies with `ERR_MODULE_NOT_FOUND` before the protocol loop starts; `spawn-lifecycle-port.test.ts:73` exercises exactly this fixture shape. The plan sees the consequence (Risks, 3770-3787) and calls it non-blocking; the auditor's position on that is that "labelling it non-blocking is a scope judgement, not a refutation", and that the counterweights offered (Task 2b's own fixture is self-contained, the pinned entry point is additive) do not refute it either. The scope lens frames the same root cause as a boundary problem: the slice's stated goal (plan 10-20) is pinned authorization, while Task 2b concedes "the defect this task closes is not in admission" (2494-2508) and the fix required is a change to how plugins are packaged. — fix: either snapshot the runner alongside the plugin and rewrite the specifier (or load the runner through a path the ticket names) and add a pinned variant of `spawn-lifecycle-port.test.ts` that proves a repo fixture actually launches; or keep this slice to pinned admission, digest re-derivation and disclosure, and defer D8/Task 2b to the phase permitted to touch the launch and supervisor seams. — **resolved by removal (cycle-5 pivot).** There is no snapshot and no new path, so there is nothing for a relative specifier to escape: the launch spec names the plugin's real directory under `pluginsRoot`, `../../../../kernel/plugin-runner/entrypoint.mjs` resolves exactly as it does on the unpinned path, and `pid-reporter` launches or fails for reasons that have nothing to do with this slice. The Risks entry that conceded the defect is gone with it. Neither branch of the offered fix was taken, because both presuppose a copy step: the plan does not snapshot the runner, does not rewrite specifiers, and does not defer Task 2b. What replaced it is `createOwnerApprovedPluginSpawnLaunchSpec` re-deriving the caller-named root's listing, `manifestDigest`, and `sourceDigest` before it constructs anything — which is where the guarantee the snapshot was carrying actually lives now. The runner file itself stays outside that guarantee, and the runner-digest Risks entry says so.

- [x] **The snapshot API has no safe per-admission cleanup handle** *(gpt:FEASIBILITY + claude:independent — reached independently by a GPT lens and the Claude reviewer, which makes this materially stronger than a single-engine finding)* — `admissionSnapshotRoot` is a local that is never returned (plan 2316-2323); the failure result carries only `{ok, code}` (1389) and the success ticket exposes only per-plugin leaf paths (2434-2437). `snapshotRoot` is documented as a shared writable parent (1394), and every test in the plan cleans up by calling `removePluginSnapshotTree(snapshotRoot)` on that shared parent (1621-1623, 2673, 3052). Two failures follow from the one missing handle. First, leaks: an admission of an empty pinned set creates a `mkdtemp` directory and returns without recording it anywhere (`schema.ts:310-343` permits an empty plugin array), and every failure return after the `mkdtemp` — 2329, 2331, 2350, 2360, 2366, 2384, 2391, 2404, 2411, 2426, 2432 — abandons a directory no caller can name; the plan's own Risks entry concedes "it is litter the caller must clean, and after cycle 4 there is strictly more of it" (~3728). Second, and worse, the only cleanup call the API makes available destroys other admissions: with two live tickets sharing one `snapshotRoot`, cleaning up after ticket A means `removePluginSnapshotTree(snapshotRoot)`, which deletes ticket B's tree too, so B's untampered plugin then throws `Error("owner-approved plugin snapshot changed after admission")` — a tamper alarm fired by ordinary housekeeping. On the Claude leg the auditor verified every citation and found no guard exists, with one qualification: "only option" is slightly overstated, since a caller could `readdir` the parent and subtract live directory names — but that is an unstated workaround, not a guard the API provides. — fix: return an opaque per-admission lease (or `admissionSnapshotRoot`) on both the success and failure results, have `removePluginSnapshotTree` accept that lease rather than a caller-supplied parent, delete the admission's own tree on every failure return, and add a test that cleans up one of two live admissions and requires the other to still verify. — **resolved by removal (cycle-5 pivot).** Both failures required a directory the admission creates and no caller can name. Admission now creates nothing: there is no `mkdtemp`, no `snapshotRoot` parameter, no `admissionSnapshotRoot` local, and no `removePluginSnapshotTree` to call — so no failure return can leak a directory, and no cleanup call can destroy another live ticket's tree. The cross-admission tamper alarm this finding described (housekeeping after ticket A making ticket B's untampered plugin throw) cannot occur, because verification re-derives from the plugin's own directory under `pluginsRoot`, which no admission owns and no cleanup deletes. The lease API in the fix was not built; it would have had nothing to hold. The `mkdtempSync` calls that remain in the plan are test fixtures creating their own temp roots, which is what they always were.

- [x] **Admission copies and fully reads untrusted plugin files before proving the pinned digest, with no byte budget and no rollback** *(gpt:SECURITY)* — `snapshotPluginTree` runs `copyFileSync` over every declared file (plan 2237-2245) before `sourceDigest` is recomputed at 2362-2366, and the generator's own read path is a whole-file `readFileSync` (`generate-plugin-registry.ts:297-306`). The auditor found no size cap anywhere in the path — the only bound in the plan is `pinned.size > 0`. Failure: point a pinned admission at a plugin tree whose declared `index.mjs` is multi-gigabyte; the bytes are copied to the snapshot root and read whole into memory before the digest mismatch is discovered, and every repeat attempt leaves another orphaned directory behind (the cleanup leg overlaps with the finding above, but the root cause here is resource exhaustion from handling unproven bytes, not the missing handle). — fix: impose a per-file and per-admission byte budget, stream the copy and the hash instead of buffering whole files, run the pin-membership and descriptor-derivation checks before anything is copied, and delete the admission's tree on every failure return. — **partly resolved by removal (cycle-5 pivot), the ordering half applied as written, the byte budget conceded.** Three of the four fixes are moot or done: there is no copy to stream and no tree to roll back, and Task 2 now orders the pin-membership check and the descriptor derivation ahead of any file read, so an unpinned or mis-described plugin is refused before a byte of it is opened. The byte budget survives the pivot and is not fixed here. Admission still calls `readFileSync` per declared file to recompute `sourceDigest`, and launch re-derivation reads the same files again — so a multi-gigabyte declared file is still read whole before the digest mismatch is discovered, now twice rather than once-plus-a-copy. That is conceded verbatim in a new Risks entry ("Admission and launch read whole files with no size budget"), which argues the residual is a resource bound rather than a trust bound — the bytes must still match the owner's pin, so an oversized file can make a refusal expensive but cannot turn it into an admission — and routes the fix to the resource-caps entry already in Deferred rather than into these functions. Streaming hashes would fix it and were not adopted this cycle.

- [x] **Snapshot trees are inaccessible to the plugin when the configured uid/gid drop succeeds** *(gpt:FEASIBILITY)* — `mkdtempSync` creates its directory `0700` owned by the admitting process (plan 2312-2323), and the leaves are `0o555` owned by the same uid (2243-2245), while `spawn-profile.json:9-10` configures uid/gid 10101 and `plugin-spawn-supervisor.mjs:316-332` applies it. The auditor notes the supervisor's fallback triggers only on EPERM/EACCES — so running as root the drop succeeds — and that "uid/gid never appear anywhere in the plan". Task 2b's tests only build a spec, so nothing in the slice exercises a real spawn under a successful drop. — fix: make snapshot ownership and traversal part of the API contract — chown/mode the admission directory for the configured launch identity or validate the caller-supplied `snapshotRoot` against it — and add an end-to-end pinned-launch test that actually performs the privilege drop. — **resolved by removal (cycle-5 pivot).** The unreachable tree was the `0700` `mkdtemp` parent and its `0o555` leaves, all owned by the admitting process; none of them exist now. The pinned launch spec points at the plugin's real directory under `pluginsRoot` — the same directory the unpinned path already spawns from, with whatever ownership and modes the deployment gave it — so a successful drop to uid/gid 10101 traverses it exactly as it does today. This slice neither improves nor degrades that; it simply stops introducing a second, more restrictive location. The end-to-end privilege-drop test in the fix was not added, and Task 2b's tests still only build a spec: that is unchanged from cycle 4 and is a supervisor-seam concern this slice is barred from touching.

- [x] **The branded disclosure renderer does not authenticate its lines against plugin stdout spoofing** *(gpt:SECURITY)* — the brand gates who may *call* `renderPluginDisclosureLines` (plan 3250-3265, 3341-3368), but the output is plain text recognizable only by its `plugin disclosure: ` prefix, and the supervisor forwards child stdout raw (`plugin-spawn-supervisor.mjs:442-470`). Failure: an admitted plugin writes a byte-identical `plugin disclosure: victim@1.0.0 kind=tool manifest=… source=… brokerCapabilities=none` line to stdout; in a shared operator log it is indistinguishable from the trusted renderer's output, so the surface whose entire purpose is telling an operator the truth about provenance can be written by the thing it describes. The auditor checked the obvious refutation and found it does not apply: the protocol frame decoder at `plugin-session.ts:195` governs the current session path, not the future composition root that would emit these lines. — fix: emit disclosure as a structured event on a trusted-origin channel rather than as prefix-recognized text, label or otherwise segregate child stdout in any shared sink, and add a test that a plugin-authored line does not satisfy the disclosure surface. — **conceded and documented; no mechanism, by owner decision.** The finding is accepted as stated, including the auditor's refutation-check: the protocol frame decoder does not govern the future composition root that emits these lines. What ships is a requirement in prose — D4 and Task 3 now state that only lines attributable to the harness's own composition root are disclosure, and that the `plugin disclosure:` prefix is a formatting convention, not a provenance claim — plus a Risks entry saying plainly that anyone sharing the harness's stdout can forge a line, that a nonce or signature would not help because a reader of a shared stream cannot attribute what the harness itself can print into it, and that the blast radius is bounded by disclosure enforcing nothing. The structured-event fix is written up as a Deferred entry naming the open questions it turns on (which channel, whether child stdout should be captured and re-emitted with attribution, what happens with no reader attached). All three of those are composition-root decisions, and the composition root is outside this slice — which is why the fix's first two clauses are deferred rather than applied. The third clause, a test that a plugin-authored line fails the surface, was not added: there is no mechanism for it to test, and a test asserting that two byte-identical strings are indistinguishable would assert nothing.
